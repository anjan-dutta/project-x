What this is, and what it isn't

This is stage one of four. It uses the browser's built-in SpeechRecognition API, which costs nothing and needs no server, which is why it runs on a static GitHub Pages site with no backend at all.

The remaining stages need infrastructure that does not exist yet:

01
Speech to text. Web Speech API, in the browser. This demo.
02
Text to a tool call. An LLM picks the function and its arguments from the transcript. Needs a server holding an API key.
03
Execute against data. The BFF runs the query. Needs Postgres and real factory data.
04
Render or narrate. Show a table for lookups; call back into the model only when the answer needs prose.
Worth noting

Recognition quality here is what stage two receives. If material names and supplier names come through garbled, no amount of model quality downstream recovers them. Try your actual SKU vocabulary, not just clean sentences, and see what survives.

Privacy

In Chrome and Edge, audio is sent to Google's speech servers for recognition. It is not processed locally, despite the API living in the browser. Nothing is sent to any server of ours, because there isn't one: this page is static files.

Transcripts stay in the page and are lost on reload. Nothing is stored anywhere. For production with real procurement data, this is one of the reasons to consider a self-hosted speech model rather than the browser API.
